## 핵심 개념 정리

### 1. 2025년 12월 = 에이전틱 코딩의 변곡점
프로그래밍의 단위가 "코드 한 줄"에서 "매크로 액션 위임"으로 바뀐 시점. 에이전트가 기능 구현·리팩토링·서비스 설정을 "도움이 되는 수준"이 아니라 "신뢰할 수 있는 수준"으로 처리하기 시작했다고 카파시는 말함.

### 2. Software 1.0 → 2.0 → 3.0
| 단계 | 프로그래밍 단위 | 인간의 역할 |
|---|---|---|
| 1.0 | 코드(함수) | 코드 직접 작성 |
| 2.0 | 데이터셋 + 신경망 | 데이터 큐레이션, 학습 |
| 3.0 | 프롬프트(문단) | 프롬프트 작성, **컨텍스트 윈도우가 곧 프로그램**, LLM은 인터프리터 |

**MenuGen 예시**: 레스토랑 메뉴 사진 → 요리 이미지 생성 앱. 기존 방식(OCR → API 호출 → UI 렌더링) 대신, 멀티모달 모델이 입력을 바로 출력으로 변환 — "많은 앱이 더 이상 존재할 필요가 없다."

### 3. 검증 가능성(Verifiability)이 자동화 순서를 결정
- 전통 소프트웨어: **명시(specify)할 수 있는 것**을 자동화
- LLM/RL: **검증(verify)할 수 있는 것**을 자동화
- 수학·코드·테스트처럼 자동 보상 신호가 있는 영역은 빠르게 개선되지만, "세차장까지 걸어가야 하나?" 같은 리셋 불가능하고 검증 어려운 일상 판단에는 최신 모델도 여전히 기본 실수를 함.

### 4. Jagged Intelligence (들쭉날쭉한 지능)
능력 수준은 다음 세 축의 상호작용으로 결정:
1. 검증 가능성
2. 학습 데이터/RL 환경에 얼마나 집중 투자됐는지
3. 경제적 가치

→ 체스 성능 향상은 "지능이 늘어서"가 아니라 "체스 데이터가 학습 믹스에 더 들어가서"일 수 있음. **벤치마크 스파이크 ≠ 범용 지능 향상.**

### 5. "동물이 아니라 유령을 소환하고 있다" (Ghosts, Not Animals)
- 동물 지능은 수십억 년 진화의 산물 (얼룩말은 태어나자마자 걷는다). LLM은 이런 식으로 자라지 않음.
- LLM은 인간이 쓴 텍스트를 압축·증류한 것에서 출발 — "성장(growing)"이 아니라 "조율(tuning)"이 필요한 존재.
- Richard Sutton 류의 "동물처럼 학습시켜라" 프레임은 LLM의 실제 작동 방식을 오독한다는 게 카파시의 반박 포인트.
- 함의: 생물학적 동기·호기심·공감이 없으므로 "한 순간 천재적이다가 다음 순간 이상하게 멍청해질" 수 있음 — 인간과 같은 신뢰 휴리스틱을 적용하면 안 됨. 필요한 자세는 **경험적 친숙성**(어디서 작동하고 어디서 실패하는지 직접 겪어보며 학습).

### 6. RL의 구조적 한계 — "빨대로 빨아먹기"
단일 스칼라 보상 신호를 시퀀스의 모든 토큰에 역전파하므로 신호가 극도로 희소하고 노이즈가 심함. 대안으로 제시하는 개념이 **"인지 핵심(Cognitive Core)"** — 세상 지식은 적지만 추론 밀도가 높은 소형(~1B 파라미터급) 모델에, 도구 사용과 검색으로 즉시 지식을 보충하는 방식.

### 7. Vibe Coding vs. Agentic Engineering
- **Vibe Coding**: 비전문가도 프로토타입/개인 도구를 만들 수 있게 함 (바닥을 높임)
- **Agentic Engineering**: 보안·품질·유지보수성을 지키며 여러 에이전트를 조율하는 전문 기술 (천장을 높임)
- MenuGen 결제 버그 사례: 에이전트가 Stripe 이메일과 Google 계정 이메일을 동일시하려 했으나 실제로는 다를 수 있음 → 영구 사용자 ID를 써야 한다는 판단은 여전히 인간 몫. **"사고는 아웃소싱 가능해도 이해는 아웃소싱 불가능하다."**

### 8. 새로 중요해지는 인간 역량
- **덜 희소해짐**: 코드 생성, API 회상, 보일러플레이트, 초안, 반복 설정
- **더 희소해짐**: 이해, 미적 판단, 평가(eval) 설계, 보안, 시스템 경계 설정, 에이전트 조율

### 9. 채용 기준의 변화
화이트보드 코딩 퍼즐은 옛 시대의 기술만 측정. 대신 필요한 역량:
- 에이전트에게 맡길 작업 분해
- 명확한 스펙 작성
- 품질 유지하며 속도 내기
- 생성된 코드 검토·보안 강화
- (제안) 실제 대규모 프로젝트, 에이전트 공격 시뮬레이션으로 평가

### 10. 에이전트-네이티브 인프라
개발 스택의 주 소비자가 인간 → 에이전트로 이동해야 함: API/CLI 중심 문서화, 기계 판독 가능한 스키마, 구조화된 로그, 안전한 권한 체계, 감시 가능한 액션. 카파시는 이를 "센서와 액추에이터"에 비유.

### 11. "9의 행진 (March of Nines)"
자율주행 비유: 신뢰도가 90% → 99% → 99.9%로 올라갈 때마다 **매번 동일한 규모의 추가 작업**이 필요함. 데모와 실제 제품 사이 격차가 왜 그렇게 큰지 설명하는 원리 — 코딩 에이전트에도 동일하게 적용됨.

### 12. 교육 — "지식으로의 경사로(Ramps to Knowledge)"
LLM을 1:1 개인 튜터 규모로 확장하는 것을 교육의 미래로 봄. 카파시 본인의 `microGPT`(의존성 없는 단일 파일 GPT 구현), CS231N, Neural Networks: Zero to Hero 등이 "정보를 이해로 전환시키는" 이 철학의 실례.

### 13. AGI 타임라인 (Dwarkesh 인터뷰, 2025-10-17)
- "인턴 수준 AI"까지 "대략 1년이 아니라 10년" — 신중한 전망
- AGI는 불연속적 사건이 아니라 경제에 서서히 섞여 들어감 (연 2%대 GDP 성장 패턴 유지 전망)

## 실무 적용 포인트 (개인 학습 관점)

1. **프롬프트를 "프로그램"으로 취급하라** — 컨텍스트 윈도우 설계가 곧 엔지니어링.
2. **에이전트에게 일을 시킬 때도 이해는 내가 해야 한다** — 결과를 검증할 수 없으면 위임하지 마라.
3. **검증 가능한 작업부터 자동화하라** — 채점 가능한 문제(코드, 수학, 테스트가 있는 작업)는 에이전트에 먼저 맡기고, 애매한 판단이 필요한 일은 직접 확인.
4. **모델의 실수 패턴은 "동물의 실수"가 아니다** — 왜 그렇게 틀렸는지 인간의 직관으로 유추하지 말고, 실제로 관찰해서 그 모델의 고유한 실패 지점을 학습하라.
5. **작은 것부터, 반복해서** — vibe coding으로 빠르게 시제품을 만들되, 프로덕션에는 agentic engineering 기준(보안·품질·감사 가능성)을 적용하라.
