# 코딩 하네스 — 생성-검증 루프

출처: 마일드코드 「클로드 그냥 쓰면 무시당합니다」(2026-07-29) → Andrej Karpathy의 LLM 코딩 실패 모드 정리 + Anthropic 공식 Best Practices.
분석 원문: `docs/Video_Analysis_VH6DsO6DdMM_클로드코드_하네스엔지니어링.md`

## 0. 전제 — 검증 수단이 없으면 그것부터 만든다

에이전트는 "다 된 것처럼 보일 때" 멈춘다. 돌려볼 수 있는 검사(테스트, 빌드 종료코드, 린터, 스크립트 출력 diff)가 없으면
검증 루프는 사람이 떠맡게 된다. 작업 시작 시 **"이 변경이 됐는지 무엇으로 확인하나?"** 에 한 문장으로 답할 수 없으면,
코드를 짜기 전에 그 확인 수단부터 만든다.

이 저장소는 통합 테스트 스위트가 없다. 그래서 최소 기준은 다음 중 하나다:
- 바꾼 스크립트를 실제로 실행해 본 로그 (`python3 <파일>` 또는 드라이런 모드)
- 최소한 `python3 -m py_compile <바꾼 파일들>` 통과
- 재현 스크립트를 `scratch/`에 만들어 수정 전 실패 → 수정 후 통과를 보여주기

**주장하지 말고 증거를 보여준다.** "동작합니다"가 아니라 실행한 명령어와 그 출력을 남긴다.

## 1. 짜기 전에 생각한다

- 가정은 말로 꺼낸다. 불확실하면 묻는다.
- 해석이 갈리면 조용히 하나 고르지 말고 선택지를 제시한다.
- 더 단순한 방법이 있으면 말한다. 필요하면 요청을 반박한다.
- 막히면 멈춘다. 무엇이 헷갈리는지 이름 붙여서 묻는다.

## 2. 단순함이 먼저다

요청을 푸는 최소한의 코드만. 추측성 확장 금지.
- 요청받지 않은 기능·추상화·설정 가능성 추가 금지
- 일어날 수 없는 상황에 대한 예외 처리 금지
- 200줄 짰는데 50줄로 되겠으면 다시 쓴다

기준 질문: "시니어 엔지니어가 이걸 보고 과설계라고 할까?"

## 3. 외과적 변경

- 주변 코드·주석·포매팅을 "개선"하지 않는다.
- 안 망가진 걸 리팩터링하지 않는다.
- 내 취향과 달라도 기존 스타일에 맞춘다.
- 관련 없는 죽은 코드를 발견하면 **말만 하고 지우지 않는다.**
- 단, 내 변경 때문에 고아가 된 import·변수·함수는 내가 치운다.

검사: 바뀐 모든 줄이 사용자의 요청으로 직접 추적돼야 한다.

## 4. 목표를 검증 가능한 형태로 바꾼다

- "검증 추가" → "잘못된 입력에 대한 테스트를 쓰고, 통과시켜라"
- "버그 수정" → "재현하는 테스트를 먼저 쓰고, 통과시켜라"
- "리팩터링" → "전후로 동일한 실행 결과가 나오는지 확인해라"

여러 단계짜리 작업이면 시작 전에 짧은 계획을 남긴다:

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
```

## 5. 이 저장소 고유 규칙

- **시크릿**: `.claude/hooks/check-secrets.sh`가 `git commit`/`git push`를 가로채 스테이징 내용의 자격증명 패턴을 차단한다.
  차단당하면 우회하지 말고 값을 제거하거나 사용자에게 확인받는다. (2026-06-22 OpenAI 키 유출 사고 재발 방지)
- **중복 생성 금지**: 새 파일을 만들기 전에 CLAUDE.md의 "알려진 폴더 중복" 절을 먼저 확인한다.
- **컨텍스트 관리**: 저장소 최상위에 UUID 폴더가 100개 이상 있다. 광범위 탐색은 `Explore` 서브에이전트에 위임해
  메인 컨텍스트를 태우지 않는다.

## 이 규범이 먹히고 있다는 신호

diff에 불필요한 변경이 줄고, 과설계로 인한 재작성이 줄고, 질문이 실수 이후가 아니라 구현 이전에 나온다.
